## 3. 私の仕様の欠陥

以下はすべて**私が書かなかったこと、または書き方を誤ったこと**である。

### S-1 BH family を「文脈ペア × 特徴量」と定義し、どちらも上限を設けなかった

実装計画書 3.3 節で、私は次を「固定する」と書いた。

```text
| L5 | （同一分割軸内の文脈ペア）×（Tier 1/2 特徴量） |
```

実装はこのとおりである（`l5.py:212` で単一 family）。

本番では context pair が約21,000、Tier 1/2 特徴量が約2,550。**universe 約5,350万、family は候補数で推定10⁵〜10⁶。**

**私は族を「上限のある設計量」ではなく「入力から自動的に決まる量」として書いた。** これが誤りである。

### S-2 仕事量の事前見積もりを契約にしなかった

実装計画書は統計手続きと閾値を書いたが、**「この計算がどれだけの仕事になるか」を申告させる仕組みを書かなかった。**

結果として、L4 の25万候補も L5 の5,350万 universe も、**実行して失敗するまで誰も気づけなかった**。

L4 には事後的に guard（R-08）が付いたが、L5 には無かった。**次の Lens でも同じことが起きる。**

### S-3 並列化を「設計の中心」と書きながら、受入基準に計算量を入れなかった

仕様概要書 決定事項25「並列化を設計の中心に置く」と書いた。
しかし実装計画書 8章の受入基準は**すべて科学的指標**（enrichment、pair 数、AUC）であり、**wall-clock も CPU 利用率も含めなかった。**

その結果、R-03 の受入条件は「全境界で 64」——**伝播の検証**になった。**消費の検証**ではない。

**これは実装 Agent の誤りではない。私が測るべき対象を指定しなかった。**

### S-4 較正値を、それが取られた設定と切り離して受入基準へ書いた

較正（診断 module）は `descriptor_set: fast` で実施した。Tier 1/2 は6空間・十数特徴量である。
本番は18空間、Tier 1/2 が9空間・推定2,550特徴量である。

**私は「L2b enrichment 2.07/2.31/2.54」という数値を、その設定を明記せずに受入基準へ書いた。**

設定が違えば enrichment も候補数も変わる。**受入基準そのものが本番に対して未検証である。**

### S-5 重複排除を文脈にだけ適用し、特徴量に適用しなかった

`feature_space_roles.md` と `candidate_generation.md` は文脈の Jaccard 重複排除を定めた。
**特徴量については何も書かなかった。**

Mordred 2D は相互に極めて高相関な記述子を約1,800列持つ。これを独立な1,800検定として扱うのは統計的に正当でない。

**同じ原理をもう一方の軸へ適用すべきだった。**

### S-6 permutation 回数 B を族サイズと無関係に固定した

実装計画書 3.2 節で B=100→1000 と固定した。**族サイズとの関係を一切書かなかった。**

B=1000 の p 値下限は `1/1001 ≈ 1e-3` である。族が大きいとこの下限が BH を通れなくなる（次章）。

## 4. 根本的な仕様修正

### 4.1 誤りの本質

仕様概要書 2.4 節で、私はこう書いた。

> **絞るべきものと、緩めるべきものを取り違えていた。**
> 0.1.x は「何を通すか」を厳しく絞り、「どう記述するか」を緩めていた。0.2.1 では逆にする。

この診断は正しい。**しかし「緩める」に上限を書かなかったのが誤りである。**

> **網羅性は無料ではない。試行数は多重比較の族サイズそのものであり、検出力を直接下げる。**

0.1.x は絞りすぎて 0 件だった。0.2.1 は緩めすぎて、**族が大きくなりすぎて 0 件になる**おそれがある。**同じ結果へ反対側から到達している。**

### 4.2 定量的な関係

BH が順位 k で棄却する条件は `p_(k) ≤ α·k/n` である。
permutation の p 値下限は `1/(B+1)` である。

最良の検定が下限に張り付いているとき、BH が棄却できる**最小件数**は次になる。

```text
k_min = n / (α (B+1))
```

言い換えると、**k 件の Finding を得たいなら族サイズは次を満たさねばならない。**

```text
n ≤ α (B+1) k
```

現在の設定で評価する。

| 設定 | n | B | α | k_min |
|---|---|---|---|---|
| 較正時（診断） | 325 | 1000 | 0.05 | **6.5** |
| 本番 L5（推定） | 600,000 | 1000 | 0.05 | **11,988** |

**本番では、p 値下限に張り付く検定が約12,000件なければ、L5 は1件も Finding を出さない。**

較正時に問題が現れなかったのは、族が325だったからである。**本番で族が3桁増えたことで、同じ手続きが機能しなくなった。**

### 4.3 修正する設計原理

仕様概要書へ次を追加する。

> **【設計原理】網羅性には予算がある。**
>
> 段階Aで「絞りすぎない」ことは正しい。しかし無制限ではない。
> 網羅的な試行には二つの予算があり、いずれも**実行前に検査する**。
>
> | 予算 | 制約 | 超過時 |
> |---|---|---|
> | **計算予算** | 仕事量の事前見積もりが Node 予算以内 | `needs_design_review` |
> | **統計予算** | 族サイズ `n ≤ α(B+1)k_min` | `needs_design_review` |
>
> `k_min` は「何件の Finding を検出できれば設計が成立するか」であり、**人間が決める設計量**である。

これにより、0.1.x の「絞りすぎ」と 0.2.1 当初の「緩めすぎ」の間に、**明示的な位置決め**が入る。

## 5. 具体的な仕様変更案

### 変更1: 特徴量の重複排除【S-5 の修正】

文脈と同じ原理を特徴量へ適用する。

```text
1. Tier 1/2 全特徴量の pairwise |Pearson r| を計算する
2. |r| ≥ 0.95 を辺として連結成分を作る
3. 各成分から代表を1つ選ぶ（Tier 昇順、次に feature ID 辞書順）
4. L5 と L1b は代表特徴量だけを使う。除外分は参照付きで記録する
```

推定効果: 特徴量 約2,550 → 数百。**族と計算量が同時に減る。**

### 変更2: L5 の比較単位を「ペア」から「文脈 vs 軸内補集合」へ【S-1 の修正】

現在は axis 内の全2組合せ（k=40 なら780ペア）を作る。
これを**各文脈とその軸内補集合の比較**（k=40 なら40件）へ変える。

| | 現行 | 変更案 |
|---|---|---|
| 比較数（k=40 の軸） | 780 | **40** |
| 問い | 「クラスタ1とクラスタ2で符号が逆か」 | 「この文脈は、同じ切り口の残りと符号が逆か」 |

**計算量が減るだけでなく、問いとして明確になる。** 780個の非独立な対比較より、「この局所だけ違う」という 0.2.1 の中心概念に近い。

推定効果: 比較数 **約19分の1**。

### 変更3: L5 の族を軸ごとに分割【S-1 の修正】

現在は L5 全体で単一 family。**軸ごとに独立な family とする。**

軸は「切り口」であり、異なる切り口の検定を同じ族に入れる統計的根拠はない。L2a が既に class × question で分割しているのと同じ考え方である。

### 変更4: B を族サイズから決める【S-6 の修正】

B を固定値ではなく、**族サイズと `k_min` から導出する**。

```text
B + 1 ≥ n / (α k_min)
```

行列形で permutation が1反復1秒未満になれば、B=10,000 でも数時間で済む。**B は最も安い調整軸になる。**

### 変更5: 仕事量の事前見積もり契約【S-2 の修正】

全 Lens が `estimate_work(inputs) -> WorkEstimate` を実装し、Runtime が Skill 起動前に検査する。
L4 の guard を Lens 共通へ一般化するだけであり、新しい概念を導入しない。

### 変更6: 較正設定の同一性検証【S-4 の修正】

較正値と一緒に、**そのとき使った設定の hash** を記録する。本番実行時に不一致を検出して警告する。

あわせて、**本番設定で較正をやり直す**。現在の受入基準（enrichment > 1.5 等）は `fast` 設定の値であり、本番に対して未検証である。

### 変更7: 受入基準へ計算量を追加【S-3 の修正】

実装計画書 8章の受入基準は科学的指標のみだった。次を追加する。

```text
worker 1 / 2 / 64 で同一の Finding 集合
wall-clock、CPU time、平均 busy CPU 数、peak RSS を記録
「workers が伝播したか」ではなく「実際に消費されたか」を検証する
```

## 6. 実施順序

```text
0. L5 を縮小設定で1回走らせ、実候補数と p 値下限に張り付く検定数を測る
       ↓ 4.2 節の k_min が現実の障害かを確定させる
1. 変更5（仕事量見積もり契約）      ← 以後の作業中に同じ事故を起こさない
2. 変更1・2・3（族の縮小）          ← 統計予算を満たす
3. 変更4（B の導出）                ← 縮小後の族に対して B を決める
4. 変更6（本番設定での較正やり直し）← 受入基準を本番に対して有効にする
5. 性能最適化（相関表の一回計算）    ← ここで初めて速度に着手
6. 変更7（受入基準の追加）
```

**性能最適化は5番目である。** 族が過大なままで速くしても、出力はゼロのままだからである。

詳細は [`CONDUCTOR_0.2.1_independent_performance_review.md`](CONDUCTOR_0.2.1_independent_performance_review.md) を参照する。

## 7. この監査が示していること

私は 0.1.x の失敗を「絞りすぎ」と診断し、0.2.1 を「緩める」方向で設計した。診断は正しかった。

**しかし「どこまで緩めてよいか」を書かなかった。**

その結果、0.1.x とは反対側から同じ場所——**Finding が出ない**——へ到達しかけている。

較正は実データで行ったが、**較正時の設定（6空間・十数特徴量）と本番の設定（9空間・2,550特徴量）が違った**。私は較正値を設定から切り離して受入基準へ書いた。これが最も直接的な欠陥である。

実装 Agent は仕様どおりに作った。**規模を書かなかったのは私である。**
