### L4 の位置づけを正確に述べる

**本番で観測された KILL は L5 である。L4 ではない。**
L4 の 25万候補は是正報告 R-08 の guard で起動前に停止しており、この点は正しく機能している。

ただし **L4 には潜在的なメモリ欠陥があり、これが候補 cap の引き上げを塞いでいる。**

- 現行 guard が見ているのは**記述子の行数と cost unit** である
- 距離行列の所要メモリは**特徴量数に比例する**が、guard はこれを model していない
- したがって cap を 100 から上げた瞬間に、guard を通過したまま OOM する

0.2.1 の目的は「中身の薄さ」の解消であり、**L4 の cap 100 は出力を直接的に細らせている。**
700 GiB の専有機を使う以上、cap を上げるのは自然な要求である。**この欠陥はそれを不可能にしている。**

## 2. L4: 3次元配列の実体化（潜在欠陥。cap 引き上げの前提）

### 2.1 欠陥

`l4.py:335` の euclidean 分岐が次を実行する。

```python
distance = np.sqrt(np.sum((normalized_right[:, None, :] - normalized_left[None, :, :]) ** 2, axis=2))
```

**`(候補数 × 観測数 × 特徴量数)` の3次元配列を作ってから合計している。**
Tier 1/2 の9空間のうち **8空間が euclidean** である（structural なのは D003 のみ）。

### 2.2 必要メモリ（コードから厳密に算出）

| 候補数 | D001（115列） | D015 Mordred（1600列） |
|---|---|---|
| 1,000 | 0.8 GiB | 11.5 GiB |
| 10,000 | 8.2 GiB | 114.6 GiB |
| 50,000 | 41.2 GiB | 572.8 GiB |
| **250,000** | 205.9 GiB | **2,864 GiB → OOM** |

**現行の既定 cap は 100 候補であり、その範囲では 1.2 GiB で収まる。落ちない。**
しかし **cap を 10,000 にすると 114.6 GiB、50,000 で 572.8 GiB となり、700 GiB でも 250,000 は落ちる。**

現行 guard（`max_candidate_description_rows` / `max_candidate_description_cost_units`）は
**記述子の計算量しか見ておらず、距離行列のメモリを model していない。**
そのため cap を上げても guard は通過し、実行時に OOM する。**cap 引き上げの前にこれを直す。**

### 2.3 修正

平方展開 `d² = |a|² + |b|² − 2ab` を使う。

```python
sq_left  = np.einsum("ij,ij->i", normalized_left,  normalized_left)
sq_right = np.einsum("ij,ij->i", normalized_right, normalized_right)
distance = np.sqrt(np.maximum(sq_right[:, None] + sq_left[None, :] - 2 * normalized_right @ normalized_left.T, 0.0))
```

| | 現行 | 修正後 |
|---|---|---|
| メモリ | 候補 × 観測 × **特徴量** | 候補 × 観測（**特徴量に依存しない**） |
| 250,000 候補 | 2,864 GiB | **1.79 GiB** |
| 計算 | 逐次 | **GEMM。全コアを使う** |
| 250,000 × 9空間の時間 | — | **1.01 分**（本機12コア実測） |

**数値同値性: 相対差 中央値 0.00e+00 / 最大 4.82e-16。** 許容幅 1e-9 を大きく下回る。

### 2.4 スコアリングも冗長である

`l4.py:392-412` の候補ループに、候補に依存しない計算が入っている。

```python
for candidate_index, candidate in generation.candidates.iterrows():
    for space_id, observed_ids, distances in spaces:
        eligible = np.asarray([i for i, v in enumerate(observed_ids) if v in endpoint_values])  # 候補に依存しない
        lexical  = np.asarray([observed_ids[i] for i in eligible], dtype=str)                   # 候補に依存しない
```

250,000 候補 × 9空間 = 225万回、**毎回 961件の走査をやり直している。**

| | 現行 | 修正後 |
|---|---|---|
| 1（候補 × 空間） | 430 μs（本機実測） | — |
| 250,000 × 9空間 | **0.27 時間** | **0.18 分**（`argpartition` で一括） |

`scipy.stats.ttest_1samp` と `t.ppf` のループ呼び出しがコストの大半である。
**近傍 k は固定なので、t 分位点は1回引けばよい。**

### 2.5 L4 に k_min 制約は適用されない

L4 の p 値は `stats.ttest_1samp`（parametric）である。**置換検定の下限 `1/(B+1)` が存在しない。**
したがって族サイズが大きくても検出力はゼロにならない。**L4 の問題はメモリと計算量だけである。**

## 4. L1b: 近傍表の再計算と単一族

### 4.1 計算量の欠陥

`l1b.py:38-44` が permutation のたびに近傍順序を計算し直している。

```python
for target in selected:
    candidates = selected[selected != target]
    order = np.lexsort((candidates, distance[target, candidates]))   # 距離は permutation で不変
```

**距離行列は permutation で変化しない。変わるのは Endpoint だけである。**
したがって近傍表は1回作れば足りる。

| 文脈サイズ m | 現行 1回 | 近傍表方式 1回 | 倍率 |
|---|---|---|---|
| 24 | 312.8 μs | 11.0 μs | 28× |
| 48 | 402.3 μs | 10.4 μs | 39× |
| 96 | 886.1 μs | 9.5 μs | 94× |
| **320** | **6,550.2 μs** | **15.4 μs** | **426×** |

現行は `O(m² log m)`、近傍表方式は `O(m·k)`。**分位分割の文脈（m≈320）で差が開く。**

```text
現行   : 611,440 回 x 加重平均 2,600 us = 0.44 時間 (1コア)
修正後 : 全文脈を1本の gather へまとめて 31.1 ms / permutation
         B=1000 で 0.52 分。近傍表メモリ 0.07 GB
```

**数値同値性: 相対差 0.000e+00（完全一致）。** 距離が同順位の場合も一致することを別途確認した。
`np.lexsort((candidates, distance))` の同順位規則が、`argsort(..., kind="stable")` を昇順の添字列へ適用したものと一致するためである。

### 4.2 族の欠陥

`l1b.py:147` は `family_key="L1b|conditional_flatness"` の**単一族**である。

候補化率を本機で実測した（231化合物、実距離行列、λ ≥ 0.50）。

```text
D001 rdkit2d   33/382 = 0.086
D003 maccs     17/382 = 0.045
D006 fragment  41/382 = 0.107
合計           91/1146 = 0.079
```

| 構成 | 族サイズ | k_min (B=1000) |
|---|---|---|
| **現行（単一族）** | 9 × 1,068 × 0.079 = **763** | **15.2** ← 目標10を超過 |
| **空間別に分割** | **84** | **1.68** |

> **L1b も統計予算を超過している。** 超過幅は L5 ほどではないが、**目標 k_min = 10 を満たさない。**

診断 Run の「候補 383」はより緩い閾値での値であり、本測定（λ ≥ 0.50）と矛盾しない。
**どちらの率を採っても超過する**（383基準なら族 2,272、k_min 45.4）。結論は率の選び方に依存しない。

## 7. なぜ64コア機での再測定を受入条件にしないか

初版は「64コア換算は線形補正であり実測が必要」と書いた。**R1.1 でこの立場を取り下げる。**

1. **本測定は本番寸法そのもので行った。** 961化合物・1,068文脈・1,494特徴量・9空間を、縮小せずに動かしている。外挿していない。
2. **12コアで足りるなら64コアでも足りる。** 修正後の実装は BLAS と numpy の一括演算であり、コア数が増えて遅くなる経路がない。本測定は**上界**である。
3. **メモリは解析的に厳密である。** 3次元配列の所要量は `候補 × 観測 × 特徴量 × 8` であり、測定の余地がない。
4. **残る差分は BLAS スレッド数だけであり、これは受入試験で測る対象であって、修正方針を決める材料ではない。**

したがって **R1.1 の修正内容は本書だけで確定できる。**
64コア機で測るのは「実際に速かったか」であり、「何を直すか」ではない。

## 8. 予算値の確定

初版で「実装者が本番機で測定して提案」としていた項目を、本測定に基づいて確定する。

| 項目 | 確定値 | 根拠 |
|---|---|---|
| **Node wall-clock 予算** | **60 分** | 修正後の最長 Node は L5 の 7.3 分。8倍の余裕を持つ |
| **Run 全体の予算** | **6 時間** | 半日利用可能との前提に対し余裕を取る |
| **Node メモリ予算** | **64 GiB** | 修正後の最大所要は L4 の 1.79 GiB。700 GiB に対し十分小さく、かつ R0 の 2,864 GiB を確実に弾く |
| **進捗報告間隔** | **5 秒**、または全体の 1% のいずれか遅い方 | L5 は 437 ms/permutation。1% = 10 permutation = 4.4 秒 |
| **stalled 判定** | **報告間隔の 20 倍。下限 60 秒、上限 600 秒** | 固定 10 分では L5 全体（7.3 分）より長く、検知器として働かない |
| **L4 候補 cap** | **記述子コストから決める**（第8.1節） | 距離行列はもはや制約にならない |

### 8.1 L4 の候補上限は記述子コストで決まる

修正後、L4 の距離計算は 250,000 候補でも 1.79 GiB / 1.0 分である。**制約は候補の記述子計算へ移る。**

Tier 1/2 の cost class 合計は候補1件あたり **99 unit** である。

| cost class | 空間 | weight | 小計 |
|---|---|---|---|
| low | D001 D003 D006 | 1 | 3 |
| medium | D012 D014 D015 | 4 | 12 |
| high | D016 | 16 | 16 |
| **very_high** | **D019 (xTB)** | **64** | **64** |

本機で実測した単位コスト:

```text
D001 rdkit-2d   8.04 ms/分子     (cost unit 1 の実測値)
D006 fragment   0.46 ms/分子
D003 maccs      0.74 ms/分子
3D 配座生成+MMFF 64.6 ms/分子    (D012/D014/D016/D019 の前提)
```

| 候補数 | 2D系のみ（64コア） | 3D配座を含む（64コア） |
|---|---|---|
| 10,000 | 0.15 分 | 0.2 分 |
| 50,000 | 0.73 分 | 0.8 分 |
| 250,000 | 3.66 分 | 4.2 分 |

**xTB (D019) を除けば 250,000 候補でも数分である。** xTB は本機に無く測定していないが、
分子あたり秒オーダーであり、250,000 候補では 64コアでも時間規模になる。

> **決定: L4 の候補記述子から cost class `very_high` の空間を除外する。**
> L4 のスコアは空間横断の最小値（保守側）を採るため、9空間が8空間になっても手続きは成立する。
> 合成されていない仮想化合物に対する半経験的量子化学計算は、そもそも根拠として最も弱い。
> 使用した空間は evidence 行に記録する。

xTB を除くと候補1件あたり **35 cost unit**（99 − 64）になる。

### 8.2 候補 cap の引き上げ

現行の既定は **100 候補 / 900 行 / 10,000 cost unit** である。**これが L4 の出力を直接細らせている。**

Node 予算 60 分のうち **20 分を候補記述子へ配分する**と、実測単位コスト 8.04 ms / 64コアから

```text
予算 cost unit = 20分 x 60秒 x 64コア / 0.00804秒 = 約 9,550,000
候補上限       = 9,550,000 / 35 unit = 約 273,000
```

| 項目 | 現行 | 改定案 |
|---|---|---|
| `candidate_cap` | 100 | **250,000** |
| `max_candidate_description_cost_units` | 10,000 | **9,000,000** |
| `max_candidate_description_rows` | 900 | **2,000,000**（250,000 × 8空間） |
| 距離行列メモリ | 2,864 GiB（Mordred, 250k） | **1.79 GiB** |
| 距離計算 | — | 1.0 分 |
| 記述子計算 | — | 約 18 分（64コア） |

**cap の引き上げは、M-12（平方展開）と M-13（xTB 除外）が入った後でのみ安全である。**
これは分離可能な判断であり、採用しなければ cap 100 のまま M-12 / M-13 だけを入れてもよい。
ただしその場合、**L4 は最大100件の候補しか見ないままである。**

### 8.3 `estimate_work` は距離行列のメモリを含めること

現行 guard の欠落はここにある。`peak_memory_bytes` に次を必ず含める。

```text
候補数 x 観測数 x 8          (平方展開後の距離行列)
候補数 x 最大特徴量数 x 8     (候補の記述子行列)
```

**特徴量数に比例する項を見落とすと、guard を通過したまま OOM する。**

## 9. 族分割の停止規則

L1b / L2a / L5 の族を分割するにあたり、**どこまで分割するか**を決める規則が要る。

> **分割は `k_min ≤ 10` を満たす最も粗い粒度で止める。**

細かく割りすぎると各族の BH 補正が緩くなり、族数ぶん偽陽性の期待値が増える。
「分割して k_min を下げる」のは目的ではなく、**統計予算を満たすための最小限の手段**である。

## 10. 測定の限界

| 限界 | 影響 | 対処 |
|---|---|---|
| Mordred と xTB が本機に無い | 特徴量数は利用者確認値、xTB コストは未測定 | Mordred は列数のみ使用。xTB は L4 から除外して回避 |
| 候補化率は 231化合物での測定 | L1b 0.079 / L2a 0.2204 は本番で動きうる | 族分割後の k_min は 1.7〜2.3 であり、率が3倍動いても目標10を満たす |
| 12コア機 | BLAS の実効並列度は本番と異なる | 本測定は上界。第7節参照 |
| 文脈の翻訳 AUC 未測定 | 文脈数 1,068 はさらに減りうる | 減る方向は安全側（族が小さくなる） |

**候補化率の感度**: L1b の族は空間別で 84。率が3倍でも 252 → k_min 5.0 で目標内。
L2a の族は 117。率が3倍でも 351 → k_min 7.0 で目標内。**結論は測定誤差に対して頑健である。**
