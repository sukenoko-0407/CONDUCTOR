## 1. 何が起きたのか

本番データ（961化合物、64コア、700 GiB 専有機）で 0.2.1 を走らせた結果、2種類の問題が出ました。

### 1.1 性能

L5 が 8 時間以上、実質1コアで回り続けました。**測定により 7.43 時間と再現できています。**

### 1.2 統計（こちらが重大）

**L5 / L1b / L2a は、直しても Finding を1件も出せない状態にあります。**

BH 補正が順位 k で棄却する条件 `p_(k) ≤ α·k/n` と、置換検定の p 値下限 `1/(B+1)` から

```text
k_min = n / (α (B+1))        n = BH 族のサイズ
```

が導かれます。**これは「棄却に必要な最小件数」です。** 族が大きすぎると、
p 値が下限に張り付いた検定が何千件もなければ BH が1件も通しません。

| Lens | 現行の族サイズ | k_min (B=1000) |
|---|---|---|
| **L5** | 556,189 | **11,113 件** |
| **L1b** | 763 | **15.2 件** |
| **L2a** | 647 | **12.9 件** |

**目標は k_min ≤ 10 です。** 設計担当が「単一の解析で最低限 Finding を10件拾いたい」と決めました。

> **L5 を 1,000 倍速くしても、出力はゼロのままです。**
> **だから統計を先に直し、性能は後に直します。** この順序を入れ替えないでください。

### 1.3 L4 について（誤解しやすいので明記します）

**本番で KILL されたのは L5 であり、L4 ではありません。**
L4 の25万候補は是正報告 R-08 の guard が起動前に停止しており、この機構は正しく働いています。

ただし L4 には**潜在的なメモリ欠陥**があります。`l4.py:335` が
`(候補数 × 観測数 × 特徴量数)` の3次元配列を実体化しています。

| 候補数 | Mordred（1600列）での所要メモリ |
|---|---|
| 100（現行 cap） | 1.2 GiB。落ちない |
| 10,000 | 114.6 GiB |
| 250,000 | **2,864 GiB → OOM** |

**現行 guard は記述子の行数と cost unit しか見ておらず、このメモリを model していません。**
したがって cap を上げた瞬間、guard を通過したまま落ちます。

## 6. 数値同値性の要件（最重要）

修正は2種類に分かれます。**混同すると検証が破綻します。**

### 6.1 値が変わってはいけないもの（実装変更）

同じ統計量を速く計算するだけの変更です。

| 変更 | 対象 | 基準 | 設計担当の実測値 |
|---|---|---|---|
| M-5 | L5 の相関値 | 相対差 ≤ 1e-9 | 3.72e-10 |
| **M-10a** | **L1b の lambda** | **完全一致** | **0.000e+00** |
| M-11a | L2a の delta | **完全一致** | 整数添字の gather。丸めが生じない |
| M-12a | L4 の距離 | 相対差 ≤ 1e-9 | 4.82e-16 |
| M-12b | L4 の lower bound / p 値 | 相対差 ≤ 1e-9 | — |

**いずれも p 値と Finding 集合は完全一致すること。**

> **M-10a の受入は「完全一致」です。1e-9 ではありません。**
> 近傍添字は「距離昇順、同距離なら化合物添字昇順」でなければなりません。
> 現行 `np.lexsort((candidates, distance[target, candidates]))` と一致させるには、
> **文脈メンバーを昇順に保ったまま `np.argsort(..., kind="stable")` を使ってください。**
> 同順位距離を含むテストケースで一致を確認すること（設計担当は整数距離行列で確認済み）。

> **M-12a では `np.maximum(..., 0.0)` を平方根の前に必ず入れてください。**
> 平方展開は丸めで負になりえます。

### 6.2 値が変わってよいもの（仕様変更）

## 7. 守ってほしいこと

### 7.1 実装してはいけないもの

| 項目 | 理由 |
|---|---|
| **process 並列化（shard / resource token / mmap）** | 修正後の置換検定コストは全レンズ合計で12コア機で約10分。shard は決定性・checkpoint・BLAS スレッドとの相互作用を増やし、**頑健性を下げます** |
| **shard checkpoint** | 修正後の最長 Node は L5 の 7.3 分。**最初からやり直せる時間であることを受入条件にしています** |
| **B（置換回数）の引き上げ** | 族縮小後は B=1000 で k_min が全レンズ 1.0〜2.3。**不要です** |
| **特徴量重複排除を統計対策として扱うこと** | 実測で族はほぼ変わりません。計算量と可読性のためだけに行います |
| **L2b / L7 の変更** | 測った上で不要と判断しました |
| **固定値の `max_units`** | データ規模が変わると意味を失います。wall-clock 換算を使ってください（M-14） |

**「一般的にはあった方がよさそう」という理由で復活させないでください。**
いずれも設計担当が検討した上で、**頑健性を下げるという理由で明示的に却下したもの**です。

### 7.2 並列化は BLAS に任せる

修正後の L5 / L1b / L4 は numpy の一括演算になります。
**`workers` は BLAS のスレッド数へ渡してください。プロセス並列は使いません。**

64コアで遅くなる経路がないことが、checkpoint を不要にしている前提です。

### 7.3 族を勝手に細かく割らない

族サイズが予算を超えたとき、**割って逃げてよいのは次の粒度までです。**

| Lens | 採用する粒度 | 割りすぎ（禁止） |
|---|---|---|
| L5 | `L5\|{axis_id}\|correlation_sign_conflict` | 空間 × axis |
| L1b | `L1b\|{space_id}\|conditional_flatness` | 空間 × axis（族が 0.4 になる） |
| L2a | `L2a\|{class}\|{transformation_id}\|{question}` | ＋ axis 別（族が 6 になる） |

> **分割は `k_min ≤ 10` を満たす最も粗い粒度で止めます。**

細かく割るほど各族の BH 補正は緩くなり、族数ぶん偽陽性の期待値が増えます。
分割は目的ではなく、統計予算を満たすための最小限の手段です。
**この粒度でも足りない場合は、族ではなく比較単位そのものを見直してください**（L5 の M-3 がその例です）。

### 7.4 パラメータをハードコードしない

M-14 の予算値（Node 60 分 / Run 6 時間 / 64 GiB / 報告 5 秒 / stalled 20倍）と
M-15 の cap 値は、すべて設定ファイルの既定値として置いてください。

### 7.5 `estimate_work` にメモリの全項を入れる

L4 の現行 guard が cap 引き上げを危険にしているのは、**特徴量数に比例する項を落としているから**です。
同じ誤りを繰り返さないでください。

```text
peak_memory_bytes に必ず含める:
  候補数 x 観測数 x 8            (距離行列)
  候補数 x 最大特徴量数 x 8       (候補の記述子行列)
  文脈数 x 特徴量数 x 8 x 枚数    (L5 の相関表)
  (空間 x 文脈 x メンバー) x k x 8 (L1b の近傍表)
```
